# Cosplay Support Agent

Отдельный сервис AI-поддержки пользователей. HTTP API и CLI используют Gemini,
агентный RAG по README/docs подключённого продукта и MCP с контекстом пользователя/тикета.

## Как работает

1. Доверенный бэкенд передаёт проверенный userId, сообщение и, при необходимости, ticketId.
2. MCP-сервер, привязанный к этому пользователю, читает только его контекст из JSON.
3. Агент получает каталог документации, сам выбирает документы и поиск BM25;
   отдельная проверка покрытия запрашивает недостающие разделы.
4. Модель отвечает с учётом платформы, версии, тикета и истории разговора;
   отдельный проверяющий сверяет утверждения и ссылки D1/D2 с прочитанными документами. Ответ
   содержит источники и needsHuman, если вопрос требует участия человека.

needsHuman — рекомендация: сервис не создаёт и не передаёт обращения оператору автоматически.
Модель может ошибаться; при исчерпании контекста retrieval.status=limit сообщает о неполноте.

## Документация продукта

README и docs берутся из отдельной копии [cosplay-2](https://github.com/Flobsterable/cosplay-2).
FAQ пользователя хранится там же в docs/support-faq.md. Копии продуктовой документации
в этом репозитории нет. Обновление копии продукта обновляет корпус следующего запроса.
Механизм поиска основан на утилитах отдельного developer assistant; сервис, API,
MCP, данные и контейнер поддержки независимы от него.

## Локальный запуск

Node.js 24, npm. Скопируйте .env.example в .env, задайте пути и SUPPORT_API_TOKEN. GEMINI_API_KEY можно добавить позже.
SUPPORT_API_TOKEN — отдельный случайный токен не короче 32 символов для доверенного бэкенда.

```bash
npm ci --ignore-scripts
npm test
npm start
npm run ask -- demo-android ticket-catalog "Почему вижу демонстрационные фестивали?"
```

Для CLI также используется .env. examples содержит только вымышленные данные.
Для сервиса создайте data/users.json и data/tickets.json по этим образцам. Не коммитьте
настоящие данные. Модель получает только платформу, версию, описание проблемы и
разрешённые диагностические поля; email и внутренние поля исключаются.

## Docker на VPS

```bash
mkdir -p data
cp examples/users.json examples/tickets.json data/
cp .env.example .env
# Заполните .env и PROJECT_PATH абсолютным путём к копии продукта.
docker compose up -d --build
docker compose ps
```

API привязан к 127.0.0.1:8091 VPS. Документы и JSON подключены только для чтения;
контейнер работает без root. Нет зависимости от контейнера developer assistant.
Для локального доступа:

```bash
ssh -L 8091:127.0.0.1:8091 user@YOUR_VPS
```

GET /health — проверка HTTP-процесса; она не проверяет доступность модели.

## API чата

POST /v1/chat, Content-Type: application/json, Authorization: Bearer SUPPORT_API_TOKEN.

```json
{
  "userId": "demo-android",
  "ticketId": "ticket-catalog",
  "message": "Почему не загружается каталог?"
}
```

Ответ: conversationId, answer, sources (path/startLine/endLine), needsHuman, reason,
context (userId/ticketId/MCP tools), retrieval (status/reason). В следующих запросах
передавайте conversationId, тот же userId и ticketId. История из запроса не принимается.

История хранится только в памяти: до 6 пар сообщений, 30 минут простоя,
до 200 разговоров; перезапуск её удаляет. История и тикет другого пользователя
недоступны. На экземпляр допускаются 2 активных ответа, один на пользователя,
до 10 запросов пользователя в минуту; превышение возвращает 429.

Ошибки: 400 неверный запрос, 401 токен, 404 недоступный контекст/разговор,
413 слишком большой JSON, 415 не JSON, 429 лимит, 502 модель/источники недоступны.
Секреты и тексты ошибок модели в ответы и логи не выводятся.

## Подключение приложения

Экран чата должен обращаться к своему бэкенду, который проверяет авторизацию,
определяет userId и вызывает этот сервис. Не вшивайте SUPPORT_API_TOKEN или ключ
Gemini в Android/Desktop клиент. Публичный TLS-шлюз и пользовательская авторизация
будут частью бэкенда приложения; этот внутренний API не является ими.

Экран приложения поддерживает тестовые сессии, описанные ниже.

## Проверка из приложения (Android / Desktop)

Агент использует [Gemini через совместимый API Google](https://ai.google.dev/gemini-api/docs/openai).
По умолчанию: LLM_MODEL=gemini-2.5-flash. Модель и LLM_BASE_URL можно переопределить.
GEMINI_API_KEY читается только бэкендом; LLM_API_KEY оставлен как совместимый резервный параметр.
Без ключа сервер запускается, /health показывает modelConfigured=false,
а чат возвращает 503 model_not_configured. Поддельных ответов нет.

### Локальная проверка

1. Склонируйте cosplay-support-agent и cosplay-2 в соседние каталоги.
2. В каталоге агента скопируйте .env.example в .env. Значения PROJECT_ROOT и PROJECT_PATH
   по умолчанию указывают на ../cosplay-2; SUPPORT_DATA_DIR=./examples.
3. Сгенерируйте SUPPORT_API_TOKEN командой ниже и вставьте результат в .env.
   Включите SUPPORT_DEMO_ENABLED=true. Добавьте GEMINI_API_KEY, когда будете готовы.
4. Выполните npm ci --ignore-scripts, npm test, npm start.
5. В приложении откройте Настройки → Поддержка. Введите адрес бэкенда и нажмите «Подключить».
   Desktop: http://127.0.0.1:8091; Android Emulator: http://10.0.2.2:8091.
   На физическом Android выполните adb reverse tcp:8091 tcp:8091 и используйте http://127.0.0.1:8091.
   HTTP на Android доступен только в debug-сборке; для release используйте HTTPS.
6. Спросите «Как добавить фестиваль в избранное?», затем «А как его убрать?».
   Проверьте ответ, ссылки на документы, продолжение диалога и кнопку «Новый диалог».

~~~bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
~~~

### Развёртывание тестового бэкенда с HTTPS

Направьте DNS-имя на VPS, откройте порты 80/443. В .env задайте PROJECT_PATH
абсолютным путём к актуальной копии cosplay-2, SUPPORT_API_TOKEN и SUPPORT_DOMAIN=support.example.com.
Включать тестовый режим вручную для этого compose не нужно: override включает его и монтирует
только examples с вымышленным demo-app. Реальные users/tickets не используются.

~~~bash
docker compose -f compose.yaml -f compose.demo.yaml up -d --build
~~~

В приложении введите https://support.example.com. Если ключ ещё не задан, приложение покажет это.
Позже добавьте GEMINI_API_KEY в .env и повторите команду с --force-recreate:

~~~bash
docker compose -f compose.yaml -f compose.demo.yaml up -d --force-recreate
~~~

Caddy получает TLS-сертификат автоматически. /health остаётся доступен только через локальный порт VPS.
Не включайте внешнее логирование тел запросов и Authorization.

### Контракт тестового API

POST /v1/sessions без авторизации выдаёт {token,expiresIn:1800,mode:"demo"}.
Затем POST /v1/chat с Authorization: Bearer token принимает только {message,conversationId?}.
Сервер привязывает сессию к demo-app; передача userId/ticketId запрещена.
История изолирована между сессиями, хранится в памяти и удаляется после перезапуска/30 минут простоя.
Токен истекает через 30 минут; в приложении потребуется подключиться заново.
Лимиты: 200 сессий, 10 новых сессий с IP в минуту, общий лимит демо-чата 10 сообщений в минуту,
один активный ответ для demo-app. При переполнении — 429/503.

Это публичный тестовый доступ, который может расходовать квоту Gemini. Включайте его на время проверки;
после проверки остановите gateway и пересоздайте основной сервис с SUPPORT_DEMO_ENABLED=false.
Для реальных пользователей сохранён внутренний /v1/chat с SUPPORT_API_TOKEN:
бэкенд приложения должен проверять пользовательскую авторизацию и выбирать userId сам.

Клиент не хранит секреты на диске и не логирует переписку. История живёт до закрытия приложения;
адрес вводится при запуске. При сетевой ошибке черновик остаётся для повтора.
Автоматического создания/передачи тикетов нет: needsHuman отображается как рекомендация обратиться к человеку.
