# Cosplay Support Agent

Отдельный сервис AI-поддержки пользователей. HTTP API и CLI используют DeepSeek,
агентный RAG по README/docs подключённого продукта и MCP с контекстом пользователя/тикета.

## Как работает

1. Доверенный бэкенд передаёт проверенный userId, сообщение и, при необходимости, ticketId.
2. MCP-сервер, привязанный к этому пользователю, читает только его контекст из JSON.
3. Агент получает каталог документации, сам выбирает документы и поиск BM25;
   отдельная проверка покрытия запрашивает недостающие разделы.
4. Модель отвечает с учётом платформы, версии, тикета и истории разговора. Ответ
   содержит источники и needsHuman, если вопрос требует участия человека.

needsHuman — рекомендация: сервис не создаёт и не передаёт обращения оператору автоматически.
Модель может ошибаться; при исчерпании контекста retrieval.status=limit сообщает о неполноте.

## Документация продукта

README и docs берутся из отдельной копии [cosplay-2](https://github.com/Flobsterable/cosplay-2).
FAQ пользователя хранится там же в docs/support-faq.md. Копии продуктовой документации
в этом репозитории нет. Обновление копии продукта обновляет корпус следующего запроса.
Механизм поиска основан на утилитах отдельного developer assistant; сервис, API,
MCP, данные и контейнер поддержки независимы от него.

## Локальный запуск

Node.js 24, npm. Скопируйте .env.example в .env, задайте пути, модель и LLM_API_KEY.
SUPPORT_API_TOKEN — отдельный случайный токен не короче 32 символов для доверенного бэкенда.

```bash
npm ci --ignore-scripts
npm test
npm start
npm run ask -- demo-android ticket-catalog "Почему вижу демонстрационные фестивали?"
```

Для CLI также используется .env. examples содержит только вымышленные данные.
Для сервиса создайте data/users.json и data/tickets.json по этим образцам. Не коммитьте
настоящие данные. Модель получает только платформу, версию, описание проблемы и
разрешённые диагностические поля; email и внутренние поля исключаются.

## Docker на VPS

```bash
mkdir -p data
cp examples/users.json examples/tickets.json data/
cp .env.example .env
# Заполните .env и PROJECT_PATH абсолютным путём к копии продукта.
docker compose up -d --build
docker compose ps
```

API привязан к 127.0.0.1:8091 VPS. Документы и JSON подключены только для чтения;
контейнер работает без root. Нет зависимости от контейнера developer assistant.
Для локального доступа:

```bash
ssh -L 8091:127.0.0.1:8091 user@YOUR_VPS
```

GET /health — проверка HTTP-процесса; она не проверяет доступность модели.

## API чата

POST /v1/chat, Content-Type: application/json, Authorization: Bearer SUPPORT_API_TOKEN.

```json
{
  "userId": "demo-android",
  "ticketId": "ticket-catalog",
  "message": "Почему не загружается каталог?"
}
```

Ответ: conversationId, answer, sources (path/startLine/endLine), needsHuman, reason,
context (userId/ticketId/MCP tools), retrieval (status/reason). В следующих запросах
передавайте conversationId, тот же userId и ticketId. История из запроса не принимается.

История хранится только в памяти: до 6 пар сообщений, 30 минут простоя,
до 200 разговоров; перезапуск её удаляет. История и тикет другого пользователя
недоступны. На экземпляр допускаются 2 активных ответа, один на пользователя,
до 10 запросов пользователя в минуту; превышение возвращает 429.

Ошибки: 400 неверный запрос, 401 токен, 404 недоступный контекст/разговор,
413 слишком большой JSON, 415 не JSON, 429 лимит, 502 модель/источники недоступны.
Секреты и тексты ошибок модели в ответы и логи не выводятся.

## Подключение приложения

Экран чата должен обращаться к своему бэкенду, который проверяет авторизацию,
определяет userId и вызывает этот сервис. Не вшивайте SUPPORT_API_TOKEN или ключ
DeepSeek в Android/Desktop клиент. Публичный TLS-шлюз и пользовательская авторизация
будут частью бэкенда приложения; этот внутренний API не является ими.

Сейчас экран приложения к сервису автоматически не подключается.
